## Ітерація 1. Вимоги та критерії приймання

**Промпт автора:** «Зроби лабораторну роботу № 5 [текст завдання]. Продовжуємо сайт „ЗнанняПлюс“ з попередніх робіт».

**Відповідь ШІ (скорочено):** ШІ відібрав із ПР № 1 вимоги, які потребують сервера, і сформулював критерії приймання:

| ID | Вимога | Критерій приймання |
|---|---|---|
| AC-1 | Каталог з фільтрами (US-01) | фільтри передаються в `GET /api/courses`, адреса сторінки оновлюється, порожній результат має окремий стан |
| AC-2 | Реєстрація та вхід (FR-04) | пароль зберігається лише як хеш, сесія — HttpOnly-cookie, невірний пароль дає загальне повідомлення |
| AC-3 | Запис і оплата (US-04) | ціну й знижку рахує сервер; немає вільних місць → 409; повторний запис → 409 |
| AC-4 | Індивідуальне заняття (US-03) | зайняті слоти беруться з БД; один слот не можна зайняти двічі |
| AC-5 | Кабінет (US-07) | скасування не пізніше ніж за 12 год (перевіряє сервер), повернення на баланс |
| AC-6 | Адмін-панель (US-08) | CRUD груп; перетин розкладу викладача → 409 з текстом конфлікту; доступ лише для ролі admin |
| AC-7 | Заявка на консультацію | зберігається в БД, адміністратор бачить і опрацьовує її |
| AC-8 | Якість | автотести API; WCAG 2.1 AA без автоматично виявлених порушень; CLS < 0,1; заголовки безпеки |

## Ітерація 2. Початковий промпт: архітектура, REST API, модель даних

**Промпт (сформульований разом із ШІ, використаний як специфікація):**

> Ти — senior full-stack розробник. Перетвори статичний сайт освітнього центру «ЗнанняПлюс»
> (14 HTML-сторінок, vanilla JS, дані в localStorage) на вебзастосунок.
> Обмеження: Node.js 22, мінімум залежностей (лише Express 5), БД SQLite через вбудований `node:sqlite`,
> клієнт залишається на vanilla JS (без фреймворків і збирання).
> 1) Запропонуй архітектуру (шари: маршрути → валідація → доступ до БД) і структуру папок.
> 2) Спроєктуй модель даних: користувачі з ролями, курси, групи курсів, записи (групові та індивідуальні),
>    заявки на консультацію, промокоди. Вкажи ключі, обмеження CHECK/UNIQUE.
> 3) Опиши REST API для CRUD кожної сутності: метод, шлях, тіло, коди відповідей, права доступу.
> 4) Безпека: хешування паролів, підписані HttpOnly-cookie, CSRF, rate limiting, CSP, параметризовані запити,
>    серверна валідація з помилками полів (422), перевірка ролей.
> 5) Бізнес-правила виконуються на сервері: ціна й знижка, вільні місця, правило 12 годин,
>    перетин розкладу викладача, слоти репетитора.
> 6) Напиши інтеграційні тести `node:test` для кожного правила.

**Відповідь ШІ:** триярусна архітектура «клієнт (браузер) → Express REST API → SQLite»; 6 таблиць
(`users`, `courses`, `course_groups`, `bookings`, `consultations`, `promo_codes`); 26 маршрутів
(див. README); модулі `security.js`, `validate.js`, `schedule.js`; 24 тести.

**Рішення автора:** прийнято. SQLite обрано замість PostgreSQL, бо для навчального проєкту не потрібен окремий сервер БД.

## Ітерація 3. Сервер і тести

**Промпт:** «Реалізуй сервер за специфікацією й запусти тести».

| Проблема, яку знайшли тести | Причина | Зміна, яку вніс ШІ |
|---|---|---|
| `node --test test/` → MODULE_NOT_FOUND у Node 22 | у Node 22 каталог не розгортається у файли | скрипт `npm test` змінено на `node --test test/*.test.js` |
| Вхід адміністратора в тестах → 401 | початкові дані брали пароль з глобальної конфігурації, а тест — свій | `open(file, { adminPassword })` — пароль передається явно |
| Час слоту на сервері в UTC не збігався з київським розкладом | хостинг працює в UTC | `process.env.TZ = 'Europe/Kyiv'` у `server.js` і `render.yaml` |
| npm-реєстр недоступний у пісочниці ШІ | обмеження мережі | для тестів ШІ написав мінімальну заміну Express (не входить у репозиторій); на комп’ютері автора використовується справжній Express |

Результат: **24/24 тести пройдено**.

## Ітерація 4. Підключення клієнта до API

**Промпт:** «Перепиши сценарії сторінок з localStorage на REST API: Fetch API, async/await, стани завантаження
й помилки, показ серверних помилок полів, перенаправлення на вхід».

**Відповідь ШІ:** новий модуль `public/js/api.js` (`ZP.api.get/post/patch/del`, клас `ApiError`, `requireUser(role)`);
переписано 10 сценаріїв сторінок; `AbortController` у каталозі скасовує застарілі запити.

Зміни після перевірки:

| Що виявлено | Зміна |
|---|---|
| Оформлення замовлення не знало ціну групи | у відповідь `GET /api/groups/:id` додано `price` |
| Блок «Завантаження…» вставлявся як `<div>` усередину `<ul>` | `statusBlock()` отримав параметр `tag: 'li'` |
| Параметр `next` на сторінці входу можна було підмінити зовнішньою адресою (open redirect) | функція `safeNext()` дозволяє лише відносні `*.html` |
| Кнопка «Продовжити з Google» імітувала вхід | замінено на чесний «Увійти як демо-учень» |

## Ітерація 5. Наскрізне тестування в браузері

**Промпт:** «Напиши e2e-сценарії Playwright для всіх критеріїв приймання й виправ знайдені помилки».

| Що виявлено | Причина | Зміна |
|---|---|---|
| Playwright не міг виконати перевірку на сторінці | CSP `script-src 'self'` блокує `eval` — захист працює | у тестовому контексті `bypass_csp=True`, на сайті CSP без змін |
| 401 у консолі браузера для кожного гостя | клієнт перевіряв сесію через `/api/auth/me` | додано `GET /api/auth/session` → `{user: null}` |
| «Invalid Date» у таблиці заявок | початкові дані зберігали дату в іншому форматі, ніж `datetime('now')` | єдиний формат `YYYY-MM-DD HH:MM:SS` |
| «Почнеться через 297 год» | відлік лише в годинах | показ днів: «12 дн 9 год» |

Результат: **35/35 e2e-перевірок пройдено**.
